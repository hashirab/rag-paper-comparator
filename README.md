# RAG Paper Comparator

A retrieval-augmented system, built with no RAG framework (no LangChain,
no LlamaIndex), that answers questions about two papers on retrieval-
augmented generation by retrieving from **both** and explicitly
reconciling what they say — with citations down to the section.

Papers used:
- Lewis et al., 2020 — [*Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*](https://arxiv.org/abs/2005.11401)
- Asai et al., 2023 — [*Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection*](https://arxiv.org/abs/2310.11511)

## The problem this solves

Ask a plain RAG chatbot "how does Self-RAG's retrieval decision differ
from RAG's?" and you get a paraphrase of whichever paper's chunks happened
to score highest — usually just one of them. This system retrieves
independently from *each* paper for every query, then forces the answer
to be structured around agreement / disagreement / what only one paper
addresses, with every claim tied back to an exact citation. If the
retrieved evidence doesn't cover the question, it says so instead of
guessing — including instead of falling back on the model's own
memorized knowledge of these (very well-known) papers.

## Why not just chunk by token count

Flat "split every N tokens" chunking is the thing this project
deliberately avoids, because it's also the thing that breaks worst on a
paper:

- A fixed window will happily straddle a section boundary, so the model
  ends up blending text from two unrelated parts of the paper.
- Equations and figure/table captions get mashed into surrounding prose
  instead of being retrievable on their own.

So parsing and chunking here work off the PDF's actual font metadata
(size, weight) to recover structure:

1. **`src/parse.py`** classifies every line of text — heading, subheading,
   body, caption, equation, or table row — using relative font size/weight,
   figured out per-paper (no hardcoded thresholds, since the two papers
   use different templates/fonts).
2. **`src/chunk.py`** groups body text by section/subsection, so a chunk
   never crosses a heading boundary, and keeps captions/equations/table
   rows as their own standalone, separately-retrievable chunks instead of
   folding them into prose.
3. **`src/embed.py`** embeds every chunk locally with
   `sentence-transformers/all-MiniLM-L6-v2` — no embedding API.
4. **`src/retrieve.py`** is a flat numpy cosine-similarity search (the
   vectors are pre-normalized, so it's a matrix multiply). At ~450 chunks
   this needs no ANN index — the point of doing this from scratch is
   seeing that a "vector database" is just a matrix at this scale.
5. **`src/compare.py`** builds the grounding prompt and calls Groq
   (`openai/gpt-oss-120b`) for generation. Retrieval and generation are
   fully decoupled — swapping the LLM or the embedding model is a one-line
   change in one file, not a rewrite.

## Known limitation: results tables

PDF text extraction flattens a 2D table into a 1D line of text, which can
scramble which number belongs to which model/column — especially in this
two-column ACL-style layout, where a wrapped table row and the start of
the next paragraph sometimes land on the same extracted line. `parse.py`
tags number-dense lines as `table_data` (instead of silently treating them
as prose) so the prompt can warn the model: cite a table number only when
the passage's own wording unambiguously ties it to a model/metric,
otherwise describe the trend without inventing a precise attribution.
This catches the clean cases; a genuinely robust fix would need
geometry-aware column extraction, which was out of scope here.

## Setup

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env   # add your GROQ_API_KEY
```

## Usage

```bash
cd src
../.venv/bin/python build_index.py   # parse + chunk + embed both papers (run once)
../.venv/bin/python cli.py "How does Self-RAG decide when to retrieve, versus RAG?"
../.venv/bin/python cli.py --show-context --k 4 "What training data does each use?"
```

## Project layout

```
papers/        the two source PDFs
src/
  parse.py     PDF -> typed elements (heading/subheading/body/caption/equation/table_data)
  chunk.py     elements -> section-respecting chunks
  embed.py     local sentence-transformers wrapper
  build_index.py  orchestrates parse -> chunk -> embed -> save
  retrieve.py  flat numpy cosine search, per-paper or across both
  compare.py   grounding prompt + Groq call
  cli.py       entry point
index/         vectors.npy + chunks.json (generated by build_index.py)
```
